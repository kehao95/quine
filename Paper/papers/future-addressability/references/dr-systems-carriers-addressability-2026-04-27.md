# Carrier Topology and System Continuity: A Study of Identity, Addressability, and State in Distributed Computing

This report is for informational purposes only and does not constitute professional engineering, security, system architecture, or operational advice. The theoretical and practical architecture of operating systems (OS) and distributed networks relies fundamentally on resolving how computational entities maintain continuity across disruptive boundary events. From the localized context of a POSIX `exec` system call to the globally dispersed routing of distributed object references, the persistence of a computational process requires a precise orchestration of state, authority, and addressability. 

### Executive Summary

To systematically address the foundational theories of continuity, identity, and addressability in distributed computing, this report isolates key analytical findings:
*   **System Boundaries and Carrier Continuity:** A comparative analysis (detailed in Section 5) demonstrates that systems are forced to choose which aspects of a process survive a disruption. While POSIX `exec` preserves identity and authority carriers, checkpoint/restore mechanisms (like CRIU) preserve state and execution carriers at the expense of endpoint stability. 
*   **State Preservation vs. Organizational Reconstruction:** Operating systems inherently dichotomize system continuity. The *State Preservation* paradigm (e.g., MOSIX, DMTCP) freezes and migrates exact memory footprints, suffering high overhead. The *Organizational Reconstruction* paradigm (e.g., Kubernetes, Actor Model) intentionally discards ephemeral execution memory, relying instead on preserved immutable blueprints and message queues to mathematically rebuild a functional state on a new node.
*   **Addressability, Authority, and Endpoint Continuity:** Canonical architectures diverge sharply here. POSIX creates "false-positive" identity handles where identifiers like Process IDs persist despite wholesale replacement of the underlying code. In contrast, object-capability models (like E and seL4) inextricably link addressability to cryptographic authority, ensuring that the right to access a mailbox or endpoint is synonymous with possessing its unforgeable reference.
*   **The Anti-Anthropomorphism Rule:** When utilizing this literature, researchers must strictly avoid cognitive metaphors. Terms like "orphan," "behavior," and "decision" must be mechanically decoded. System continuity is not equivalent to biological survival; it is the mathematically deterministic execution of a protocol across contiguous physical or logical memory boundaries.

Research into process migration, capability systems, and the actor model reveals that a system's resilience is largely defined by how it handles transitions. This comprehensive report examines these computational theories through the specific framework of *carrier topology*. By deconstructing systems into discrete functional carriers—source, execution, future-task, state, tool, endpoint/mailbox, and authority/capability—we can analyze how canonical architectures (such as POSIX, seL4, MOSIX, and E) either preserve system state or reconstruct organizational function following a disruption. 



## 1. Carrier Topology: An Analytical Framework

To evaluate how systems manage continuity across boundary events (such as crashes, migrations, or systemic transformations), it is necessary to decouple the monolithic concept of a "process" into a topology of distinct operational carriers. Each carrier encapsulates a specific dimension of the system's existence, and different OS or distributed models prioritize the persistence of different carriers during a boundary transition. 

### 1.1 Source and Execution Carriers
The **source carrier** represents the immutable blueprint of a computation, typically embodied in static binary files, shell scripts, or bytecode. It is the inert definition of potential behavior. Conversely, the **execution carrier** is the active realization of that source—the CPU context, program counter, and active thread scheduler allocations that drive computation forward. 

### 1.2 State and Tool Carriers
The **state carrier** encompasses the mutable memory footprint of an entity. This includes the heap, the stack, dynamically allocated memory pages, and localized variables [cite: 1]. The **tool carrier** refers to the environmental dependencies necessary for execution, such as dynamically linked libraries, system call interfaces, and the underlying OS kernel. When migrating a process across heterogeneous environments, decoupling the state carrier from a highly localized tool carrier is historically one of the most difficult challenges in distributed OS design [cite: 2, 3].

### 1.3 Endpoint/Mailbox and Future-Task Carriers
In concurrent and networked topologies, entities must communicate asynchronously. The **endpoint/mailbox carrier** provides a stable address to which messages can be sent, independent of the entity's current execution status. Strongly associated with the Actor model [cite: 4], the mailbox buffers incoming messages. The **future-task carrier** represents the backlog of pending operations—promises, continuations, or queued messages—that guarantee a computation will eventually be executed once resources become available or an execution carrier is re-established.

### 1.4 Authority/Capability Carrier
An entity's ability to manipulate its environment is defined by its **authority/capability carrier**. This includes security tokens, access control lists (ACLs), or unforgeable cryptographic capabilities. This carrier dictates what tool carriers or external state the entity is legally permitted to invoke or modify [cite: 5]. In POSIX systems, file descriptors act as highly localized authority carriers, granting access to specific I/O resources [cite: 6, 7].

## 2. Preserving State Versus Reconstructing Organization

When a system faces a disruption—whether an intentional process migration for load balancing or an unexpected hardware failure—it must achieve continuity. The literature demonstrates a fundamental architectural schism in how continuity is achieved: systems generally optimize for either *preserving state* or *reconstructing organization*.

### 2.1 The State Preservation Paradigm
State preservation assumes that the mutable memory and exact execution context of a computation are too valuable, complex, or opaque to be easily recreated. Therefore, the system must capture, transfer, and restore the exact memory footprint of the state carrier. 

**Process Migration and Checkpoint/Restart (C/R):**
Early distributed operating systems like Sprite and MOSIX (Multicomputer Operating System for UNIX) pioneered transparent process migration [cite: 2, 8, 9, 10]. In MOSIX, migration algorithms automatically shift processes to underloaded nodes to optimize cluster performance [cite: 2, 11]. To achieve this, the system must capture the entire state carrier (the process address space). Eager migration strategies copy the entire address space upfront, which can impose significant latency. For instance, empirical data from Sprite and MOSIX environments running on DECstation 3100 or SPARCstation 1 hardware demonstrates that while migrating a small passive object takes approximately 12 milliseconds, a remote `exec` transferring an active process takes 40 to 50 milliseconds, and complete evictions can take several seconds [cite: 9, 12, 13, 14]. Modern optimization protocols, such as TRAMP, use pre-copy memory iteration to dramatically reduce this "freeze time"—cutting the average halt time of an execution carrier from 41.1 seconds in legacy approaches down to a mere 213 milliseconds [cite: 15].

Similarly, modern container orchestration utilizes tools like CRIU (Checkpoint/Restore In Userspace) and DMTCP (Distributed MultiThreaded Checkpointing) [cite: 2, 16, 17]. CRIU is notable because it operates entirely in user space, using interfaces to the Linux `/proc` filesystem to iterate over a process tree, dump memory pages, and later reconstruct the hierarchy using the `fork` system call [cite: 16]. DMTCP similarly implements user-level checkpointing but specializes in complex distributed resources, creating wrapper libraries to virtualize and preserve socket states, InfiniBand connections, and MPI (Message Passing Interface) communications [cite: 18, 19]. The defining characteristic of state preservation is its *opacity*. The system does not need to understand the logic of the application; it merely treats the state carrier as a raw block of data to be replicated.

### 2.2 The Organizational Reconstruction Paradigm
Conversely, organizational reconstruction operates on the philosophy that raw state is ephemeral and easily corrupted. Instead of preserving the exact memory pages, these systems preserve the *blueprint* and the *event log*, allowing the organization to rebuild its functional state following a disruption.

**Service Failover and Crash-Only Software:**
In modern microservice topologies, if a node fails, the system does not attempt to resume the exact memory state of the failed process. Instead, the execution carrier is allowed to die. The system relies on the future-task carrier (e.g., external message brokers like Kafka or RabbitMQ, which act as intermediate systems to queue and persist asynchronous data between services) and the source carrier (a container image) to spin up a completely new instance of the service. 

**The Actor Model:**
Gul Agha’s seminal work on the Actor model of concurrent computation provides a theoretical foundation for this approach [cite: 4]. In an Actor system, the state is encapsulated strictly within an actor, which only interacts via asynchronous messages. If an actor crashes, a supervisor can spawn a new actor with the initial source carrier. By replaying the future-task carrier (the mailbox of queued messages), the new actor reconstructs the organizational state mathematically. This structural reconstruction provides far greater resilience against cascading failures, as it strictly defines and limits the blast radius of a fault.

## 3. Addressability, Authority, and Endpoint Continuity

The persistence of an identity handle—the name or address by which an entity is known—is critical for distributed continuity. However, canonical sources treat the relationship between addressability, authority, and identity in vastly different ways, often creating scenarios where identity is a "false-positive."

### 3.1 POSIX `exec` and Inherited File Descriptors
In the UNIX/POSIX environment, process creation and transformation are managed via the `fork` and `exec` system calls [cite: 6, 20]. When a process calls `exec`, the OS replaces the current process image (the source and state carriers) with a completely new program [cite: 7]. 

However, the operating system maintains the same Process ID (PID) and, crucially, keeps standard file descriptors (such as 0, 1, and 2 for stdin, stdout, and stderr) open and attached to the process unless explicitly flagged with "close-on-exec" [cite: 21, 22, 23]. This architectural decision was a historical and mechanical necessity designed to enable UNIX shell pipelines (e.g., piping output from `ls` to `grep`). By keeping file descriptors open, a parent shell can set up the piped file descriptors before calling `exec` on the child processes, ensuring the newly instantiated programs inherit the pre-plumbed I/O channels without needing to actively route them [cite: 21].

This creates a distinct carrier topology event:
*   **Replaced:** Source carrier, State carrier, Execution carrier (partially, as the instruction pointer resets).
*   **Preserved:** Endpoint identity (PID) and Authority carrier (file descriptors).

The persistence of the PID is a prime example of a **false-positive identity handle**. To an external observer monitoring the PID, the process appears to possess unbroken continuity. In reality, the entity's fundamental nature has been completely eradicated and replaced, inheriting only the authority carriers of its predecessor. 

### 3.2 Capability Systems and Distributed Object References
Traditional OS architectures rely on Access Control Lists (ACLs), where an authority monitor checks a user's ambient authority against a list of permissions. Capability systems—such as EROS (Extremely Reliable Operating System) and the formally verified seL4 microkernel—fuse addressability and authority into a single, unforgeable cryptographic token [cite: 5, 24, 25]. 

In a capability system, possessing the reference (the address) *is* the authority to invoke it [cite: 26, 27, 28]. Mark S. Miller's work on Robust Composition outlines how these capabilities function as distributed object references [cite: 29, 30, 31]. To ground this abstract concept in observed reality, one can look at everyday applications: an unguessable sharing URL (such as a private, link-sharing option in Google Workspace) acts as a literal object capability. Possessing the specific link string inherently grants the authority to view the document, bypassing centralized ambient login checks [cite: 32]. 

In mission-critical environments, the DARPA HACMS (High-Assurance Cyber Military Systems) program provides a definitive case study of this topology [cite: 33, 34]. DARPA engineers used the seL4 microkernel [cite: 33] to protect an autonomous quadcopter (the SMACCMcopter, utilizing a 3D Robotics Iris+ and elements of Boeing's Unmanned Little Bird helicopter) [cite: 35]. The system was segregated: flight control software ran on an eChronos RTOS, while the external-facing mission software ran on seL4 atop a TK1 mission computer [cite: 34, 35]. At the DEF CON hacker convention, "Red Team" hackers were intentionally granted full access to an untrusted virtual machine hosting the drone's camera feed [cite: 33, 34]. Because seL4 mathematically isolates capability carriers, the hackers were completely unable to escalate their privileges to access the flight control endpoints. The authority carrier could not be forged, proving that capability-based continuity structurally contains compromises without relying on brittle ACLs [cite: 33, 36].

### 3.3 Endpoint Identity in the Actor Model and Naming Systems
In distributed systems, physical network addresses (IPs, MAC addresses) are brittle tool carriers. If a process migrates, its physical address changes. Canonical naming systems like CORBA (Common Object Request Broker Architecture) and JNDI (Java Naming and Directory Interface) solve this by acting as registries that map human-readable names to distributed object references [cite: 37].

The Actor model provides a deeper theoretical treatment of endpoint continuity. An actor’s identity is strictly synonymous with its mailbox address [cite: 4]. The execution carrier (the thread processing the messages) and the state carrier (the actor's local variables) are entirely decoupled from the mailbox. When an actor processes a message, it specifies a "replacement behavior" for the next message [cite: 4]. Therefore, the entity is in a constant state of atomic reincarnation, yet its endpoint identity (the mailbox) remains continuous.

## 4. Modern Cloud-Native Topologies: Kubernetes and etcd

Applying the carrier topology framework to modern, ubiquitous infrastructure uncovers exactly how systems like Kubernetes achieve high availability through strict architectural compartmentalization [cite: 38, 39, 40].

In Kubernetes, the control plane components (the API Server, Scheduler, and Controller Manager) are entirely stateless tool and execution carriers [cite: 41]. The absolute **State Carrier** of a Kubernetes cluster is `etcd`, a distributed key-value store [cite: 39, 40]. Every pod definition, secret, lease, and node registration is written to `etcd` first. To prevent split-brain continuity errors, `etcd` relies on the Raft consensus algorithm, requiring a strict mathematical quorum (calculated as $\lfloor n/2 \rfloor + 1$) to elect a leader and accept writes [cite: 39, 41]. If `etcd` fails or loses quorum due to disk latency, the entire control plane halts; the system does not degrade gracefully, it stops, highlighting that state continuity is bottlenecked by disk IOPS [cite: 41].

Conversely, the worker nodes and Pods represent highly disposable **Execution Carriers** and **Source Carriers** (container images). During a node failover event, Kubernetes does not attempt to migrate the live memory state of a Pod [cite: 38, 40]. If a node fails a Liveness or Readiness probe [cite: 38], the node is marked unschedulable, and the execution carrier dies. The control plane relies on the declarative state stored in `etcd` to reconstruct the organization by scheduling a new Pod on a healthy node [cite: 38, 40]. This perfectly mirrors the *Organizational Reconstruction Paradigm*, intentionally sacrificing localized state continuity for broader systemic resilience. 

## 5. System Comparison: Boundaries and Carrier Continuity

To synthesize these distinct approaches to system continuity, we must evaluate them comparatively. The following table provides a structured breakdown of how different canonical architectures handle boundary events, identifying which carriers persist, which act as the objects of continuity, and how false-positive identity handles manifest.

**Table 1: System Boundaries and Carrier Continuity**

| System Architecture | Disruptive Boundary Event | Future Carrier Mechanism | Primary Continuity Object | False-Positive Identity Handle |
| :--- | :--- | :--- | :--- | :--- |
| **POSIX (`exec`)** | System call replacing the memory image. | Piped streams; wait/signal queues. | Authority (Inherited File Descriptors). | **PID:** Remains identical despite the program binary and memory state being entirely replaced. |
| **C/R (DMTCP / CRIU)** | Process freeze and serialization to disk. | Saved image file written to persistent storage. | State (Memory pages, heap, stack). | **Restored IP/Sockets:** May clash if restored on a network where the previous IP was reassigned. |
| **Process Migration (MOSIX)** | Preemptive relocation for load balancing. | Demand-paging queue; forwarded IPC messages. | Execution & State (Address space transferred). | **Residual Node Proxy:** The origin node acts as a proxy, hiding the true physical location of the execution. |
| **Actor Model (Agha)** | State mutation / Crash of current behavior. | Mailbox (buffers pending asynchronous messages). | Endpoint (The Mailbox Address). | **Mailbox Address:** Points to the same address, but the underlying behavioral state is replaced upon each message. |
| **Microkernels (seL4)** | Fault in isolated compartment. | Exception handlers / supervisor thread queues. | Authority (Cryptographic Capabilities). | **Compartment ID:** Remains stable while the internal execution thread may be restarted. |
| **Kubernetes (etcd)** | Node failure / Network partition. | Raft consensus queues / API Server watch states. | State (etcd database) & Source (Container Image). | **Service Endpoint:** An unchanging Virtual IP routes traffic to entirely different, newly instantiated underlying Pods. |

**Synthesis of Table 1:**
The table illustrates that no system maintains absolute continuity across all carriers simultaneously. Checkpoint/Restart and migration systems (like MOSIX and CRIU) prioritize the *State* and *Execution* carriers, accepting high overhead to ensure the entity does not realize it has been moved [cite: 2, 16]. In contrast, models designed for highly concurrent, fault-tolerant networks (Actors, seL4, Kubernetes) treat the execution carrier as expendable. They rely on the persistence of *Endpoint* (mailboxes) and *Authority* (capabilities) carriers to rebuild state organizationally.

## 6. Avoiding the Anthropomorphic Trap: Agency and Life in Computing

When analyzing the persistence, migration, and behavior of computational processes, the literature frequently employs vocabulary borrowed from biology, sociology, and cognitive science. Terms such as "identity," "behavior," "migration," "delegation," and "orphan" invoke a cognitive framework that subtly implies autonomy, life, or localized agency. To utilize this literature accurately without overclaiming life or agency, researchers must strictly decode systemic jargon into mechanical operations. 

### 6.1 Mechanical Determinism vs. Cognitive Choice
A process does not "decide" to migrate. In systems like MOSIX, a distributed load-balancing algorithm evaluates a heuristic against a threshold and mathematically forces a process relocation [cite: 2, 11]. The process is a passive data structure acted upon by the OS tool carrier. Ascribing agency to the process obscures the reality that the system's hypervisor or kernel is the active mechanical operator. 

### 6.2 De-anthropomorphizing "Authority" and "Capabilities"
In security architectures, a capability is not a "permission" in the human sense—it implies no trust, morality, or social contract. It is a mathematically unforgeable cryptographic key or an OS-protected pointer [cite: 5, 26]. The "Confused Deputy" problem sounds like a psychological failure of a human actor. In reality, it describes a mechanical vulnerability where ambient authority is blindly applied to an improperly validated external input [cite: 5, 28]. 

### 6.3 Behavior as a State Transition
In the Actor model, an actor defines its "replacement behavior" [cite: 4]. While the word "behavior" implies a sentient pattern of action, in this context, it strictly means a function pointer mapping the next incoming message to a specific output state. System continuity is not "survival"; it is the unbroken execution of a mathematical protocol across contiguous physical or logical memory boundaries.

## 7. Future Outlook: WebAssembly and the Cloud-Edge Continuum

Looking forward, the strict boundaries defined by traditional tool carriers (the underlying OS and Instruction Set Architecture) are being dissolved by the emergence of WebAssembly (Wasm) [cite: 42, 43, 44]. Originally confined to web browsers, Wasm now functions as a universal, machine-independent format that standardizes both the Source and Execution carriers [cite: 42, 43]. 

Through standards like WASI (WebAssembly System Interface) and community extensions like WASIX, the Wasm sandbox has regained the ability to securely manage processes, threads, and network sockets [cite: 42, 45]. Because the Wasm execution state is completely decoupled from the host machine's physical hardware architecture, it presents unprecedented opportunities for live process migration across the "cloud-edge continuum." Experimental frameworks now utilize Wasm to perform pre-copy and post-copy live migrations of active computational modules from central cloud servers directly to edge devices (e.g., IoT hardware) with virtually zero interruption, achieving a level of hardware-agnostic carrier mobility that legacy systems like Sprite or MOSIX could only simulate through heavy kernel modification [cite: 42, 45, 46].
