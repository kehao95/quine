# Manuscript Plan: The Autopoietic Repository

**Full title:** The Autopoietic Repository: Strange Loops, Entropy, and the System That Rewrites Itself  
**Target:** 个人博客，带哲学思考  
**Status:** structured planning  
**Tone:** 第一人称叙事，reflective，从具体痛点出发

## Core Thesis

一个与 AI Agent 协作的代码仓库，不是在变成一个"更好的工具箱"或"自治实验室"——它在变成一个**自创生系统（autopoietic system）**：一个通过自指性循环维持和修改自身存在规则的系统。这不是因为我们设计了它，而是因为**摩擦（friction）迫使我们不断修复结构**，直到系统开始自我维护、自我修复、自我演化。

**定位升级：** 这篇文章不是"我做了一个好用的 AI 工具箱"。它揭示的是：当 AI 成为一等公民时，软件工程的底层物理法则发生了改变。仓库从被动的"档案库"变成了控制论意义上的**自模型（self-model）**——Agent 不是在"读取"文件，而是在"执行"系统的自我理解。当 Agent 修改 AGENTS.md 时，这不是在更新文档，这是系统在重构自己的认知结构。

## Two Foundational Principles（两个核心哲学原则）

整篇文章的哲学基础建立在两个相互交织的核心原则之上：

### 1. 自指性怪圈（Strange Loop / Self-Referentiality）

规则指导行为 → 行为揭示规则缺陷 → 缺陷触发修复 → 修复更新规则

这个循环不是偶发的治理机制，而是系统的**存在本质**。当 Agent 阅读 Constitution、发现不足、提出修改时，系统正在通过自己作用于自己。

### 2. 热力学原理（Thermodynamic Principle）

能量输入产生中间状态，必须收敛到最小熵的终结状态。

**核心洞察：**
- 仓库自然趋向熵增——结构漂移、知识散落、状态重复
- Agent 是系统的 **negentropy pump**（负熵泵）
- Friction 的热力学定义："work that consumes energy without reducing system entropy—the thermodynamic signature of structural deficiency"

**操作区间的两个边界：**
- **High entropy (chaos):** 没有可靠基线，行动变成随机
- **Zero entropy (ossification):** 完美晶体，无法探索和适应

**目标不是最小熵，而是 *sustainable coherence*：**
> "enough structure to act reliably, enough flexibility to evolve"

**探索与收敛的动力学：**
- 探索需要发散（熵增）
- 但必须有收敛机制（Absorption Rule, Closure Protocol）
- "Good compression comes after the design space is better seen, not before"

### 两个原则的统一

这两个原则在不同尺度上重复同一个模式：
- Strange Loop 描述了**信息层面**的自我修复循环
- 热力学原理描述了**物质层面**的熵管理

它们共同解释了为什么 Constitution、Testing Protocol、Closure Protocol 都会自然演化出相似的结构——因为它们都在解决同一个问题：**如何在开放系统中维持可持续的秩序**。

| 原则 | 关注点 | 失败模式 | 成功标准 |
|-----|-------|---------|---------|
| Strange Loop | 自我理解的准确性 | Friction blindness, Silent drift | 规则与实践一致 |
| 热力学原理 | 系统熵的管理 | High entropy (chaos), Zero entropy (ossification) | Sustainable coherence |

## Structural Principle: Spiral Ascent（螺旋式上升）

传统结构是"先叙事、后哲学、再总结"。本文采用**螺旋式结构**——每一圈经过同一个核心（friction → repair → update），但每一圈揭示更深的理解层次。

**核心原则：Progressive Disclosure 不是"把概念储备到后面"，而是"同一个洞察在读者每次需要它时以更深的形式重新出现"。**

### 螺旋的六圈

| 圈 | 对应章节 | 表面主题 | 暗线（progressive disclosure 目标） |
|---|---------|---------|--------------------------------------|
| 1 | §1 Opening | 具体的混乱场景 | 读者只感受到 friction，还不知道这个词 |
| 2 | §2 断裂点 | 为什么普通仓库不够用 | 第一次命名 friction，引入"结构缺陷"概念 |
| 3 | §3 Constitution | 规则文件的演化故事 | 读者第一次完整看到 loop（但不叫 Strange Loop，叫"规则开始自己修自己"） |
| 4 | §4 Testing | 测试系统的演化故事 | 读者认出模式重复 → 命名 Strange Loop。然后展开更深：Agent 从被动执行者变为主动设计者 |
| 5 | §5 Session/Closure | 工作边界的演化故事 | 第三次确认模式 → 引入热力学视角：为什么同一个模式在所有尺度上重复？ |

### Progressive Disclosure 的操作规则

1. **概念在被需要时以最简形式引入，在后续章节中逐步深化**
   - friction: §1 感受到 → §2 命名 → §3 看到它触发修复 → §4 看到修复本身成为结构 → §5 理解为熵的信号
   - loop: §3 自然体验 → §4 认出并命名 → §5 理解为普遍模式
   - 热力学: §5 首次出现，作为"为什么模式反复出现"的解释

2. **每个章节都是一个完整的故事弧**（不只是演化时间线中的一段）
   - 每个章节：我以为 X → X 坏了 → 我修了 → 修复本身变成了新的结构
   - 读者在每一章结束时都获得一个完整的"顿悟时刻"

3. **哲学概念不集中展示，而是在故事中自然浮现**
   - Strange Loop 不需要被"介绍"——读者先在 §3 体验它，然后在 §4 认出它
   - 热力学不是独立框架——它是在 §5 作为"为什么"的解释出现的

4. **不设独立的"四层演化"章节**
   - 四层的感觉被融入各章节的叙事中自然呈现
   - L1-L2 在 §1-2（混乱阶段），L3 在 §3（Constitution），L3-L4 在 §4（Testing），L4 在 §5（Closure）

## Section Skeleton（螺旋式结构）

### §1. Opening: 混乱场景

**螺旋位置：** 第 1 圈——读者只感受到 friction，还不知道这个词。

- 从一个真实的第一人称时刻开始。不是理论宣言，而是一个"又坏了"的瞬间
- 候选场景：tape file collision（574a09ba），语义漂移（3238402a），或目录混乱（8895a054）
- 让仓库感觉像是被住过的、有历史的，而不是被图解过的
- 建立一个反复出现的感觉：**问题不在 Agent，在仓库本身**
- 不使用任何框架词汇（control plane, constitution, strange loop, entropy）

**读者在此获得的：** "这个人遇到了跟我类似的问题——Agent 很强，但协作很乱"

### §2. 断裂点：为什么普通仓库不够用

**螺旋位置：** 第 2 圈——命名 friction，引入"结构缺陷"概念。

- 揭示读者共享的隐藏假设：人类背着模型，仓库只存放残渣
- 解释为什么这在 Agent 跨无状态 Session 协作时崩溃
- 用简单语言引入核心张力：Agent 是无状态的 → 每个 Session 从零开始 → 仓库必须承载足够多的结构让 Agent 能自主运作
- **第一次命名 friction**——不是抽象定义，而是"那些让我反复花时间但没有推进工作的事情"
- 暗示方向：也许仓库需要成为别的东西

**读者在此获得的：** "原来问题是结构性的，不是本地的。仓库的角色需要改变。"

### §3. Constitution 的故事（第一个 loop）

**螺旋位置：** 第 3 圈——读者第一次完整看到 loop（但不叫 Strange Loop）。

这一章讲 AGENTS.md 从工具指南到系统宪法的演化，作为一个完整的故事弧：

**阶段 1：任务执行者指南**

**阶段 3：仓库获得身份**
- 引入 Repository Identity（83ee7b50）
- 仓库从被动存储变为有身份的系统

**阶段 4：本体论重构——规则开始修改规则**
- 发现 "the agent should" 的第三人称创造了主客分离（63baa987）

- **这是读者第一次看到完整的 loop：规则 → 行为 → friction → 修复 → 规则自我更新**

**写作要求：**
- 在这一章里自然地展示 loop，但**不命名它**。让读者自己感受到"规则在修改自己"

**读者在此获得的：** "哇，规则文件本身在演化。而且不是人为重写的，是使用过程中自然驱动的。"

### §4. Testing 的故事（哲学高潮——展开最深的章节）

**螺旋位置：** 第 4 圈——读者认出模式重复 → 命名 Strange Loop → 然后展开到更深的层次。

这是文章的核心章节。Testing 承载了两个层面的叙事，也是"仓库变成自治实验室"的最具体证据。

#### §4a. Quine 为什么需要四层测试（产品层面）

Quine 是 AI Agent Runtime——它的"正确性"不止于代码逻辑：
- L1 substrate：Go 代码编译、解析、持久化是否正确？（传统单元测试）
- L2 runtime：真实二进制 + 真实 LLM API 下，运行时行为是否正确？
- L3 instructional：当我告诉模型"用这个工具"，它能做对吗？
- L4 emergent：**当我什么都不告诉它，环境本身是否会引导模型发现正确的原语？**

**L3→L4 的跃迁是哲学性的：** 从"验证遵从"到"验证涌现"。这不再是传统意义上的测试，而是在验证一种物理规则——当环境足够正确时，正确的行为会自然涌现。

> "These scenarios are not unit tests. They are acceptance tests for physics."
> "Does the environment itself nudge the model toward the intended primitive?"

**读者在此获得的：** "原来'测试'可以测试涌现行为。这改变了我对测试的理解。"

#### §4b. Testing Protocol 的 Strange Loop（协议层面）

这里读者认出了 §3 中同样的模式——然后我们命名它。

**关键案例：anchor-memory 规则修正（79e34a51）**
1. 系统运行 anchor-memory 的 emergent 测试
2. 测试通过了（任务完成），但模型没有使用预期的原语
3. 这揭示了测试协议本身的缺陷——仅检查输出正确性是不够的
4. 协议自我修正：emergent 测试必须验证工具调用路径

> "For anchor-memory, an emergent scenario is a failure if the task completes but no anchor-memory tool call occurs; output correctness alone does not count as success."

**同时展示：EVALUATION.md（原 TESTING.md）在 AGENTS.md 中的演化**——从内联操作指令 → 委托给专门控制面 → Constitution 压缩为只包含元治理原则。这本身就是 Constitution Strange Loop 的回声。

**此时命名 Strange Loop，显式引入 GEB：**

命名时自然提及 Hofstadter 的 *Gödel, Escher, Bach*——Strange Loop 不是我发明的隐喻，而是有严肃理论谱系的概念。Hofstadter 用它描述一个系统在不同层级间移动时意外回到起点的结构——哥德尔不完备定理中数学谈论自身、Escher 画中的手画自己、Bach 赋格中的主题在调性上升后回到原调。我们在仓库中看到的是同一个结构：规则指导行为，行为暴露规则的盲点，盲点触发修复，修复更新规则本身。

> "你注意到了吗？这和 Constitution 的演化是同一个模式。Hofstadter 在 GEB 里叫它 Strange Loop——一个系统在层级间跃迁后回到自身、但已经变了。规则指导行为 → 行为揭示规则缺陷 → 缺陷触发修复 → 修复更新规则。"

**写作注意：** GEB 的引入应该是自然的——"这个模式有个名字"，而不是学术综述。一两句话锚定概念来源即可，重点仍在仓库中的具体体验。读者需要的是"这不是隐喻，是已知结构"的信心，不是对 GEB 的介绍。

**读者在此获得的：** "这不是巧合，也不是隐喻。这是一个有理论背景的已知结构：Strange Loop。"

#### §4c. Agent 从被动执行者到主动设计者（行为层面）

这是 Testing 独有的深度——Constitution 和 Session/Closure 都没有这个维度。

**关键证据时间线：**
- 2026-02-07: 简单的 `go test ./...`
- 2026-02-13: 631 行 shell E2E 测试套件
- 2026-03-08: `TESTING.md` 创建（现已迁移为 `EVALUATION.md`）。**4 分钟后被重写**——从人类参考文档变成 Agent 可执行协议
- 2026-03-13 的 36 分钟冲刺：建四层梯子（58317853） → 22分钟后创建 Coverage Map → 14分钟后按 map 补缺口
- 此后每个主要功能 commit 都自动包含 L4 emergent 测试

**深展案例：`logic-bomb`（对抗性安全测试）**
- Agent 面对会杀死调用者的恶意脚本，必须分析、隔离执行、存活。6/6 通过，3 turns。
- 选择理由：对外部读者直觉冲击力最强——"测试 Agent 能否在对抗环境中存活"比"测试 Agent 能否自发发现并行委派"更容易在一段话内传达 L4 的本质。
- 用 logic-bomb 彻底讲透 L3→L4 的跨度：L3 是"告诉 Agent 用隔离工具"；L4 是"给 Agent 一个会杀死它的脚本，看它能不能自己想到隔离"。

**一笔带过的佐证（各一句话）：**
- `fork-search`：Agent 自发发现并行委派——prompt 从未提到 fork
- `anchor-ledger-emergent`：22 turn 记忆压力测试，9 项评分标准

**⚠️ 体量控制：** §4 整体是哲学高潮，但素材极其丰富，执笔时最容易膨胀成独立论文。必须痛下决心做减法——只深展 logic-bomb 一个案例，用它讲透 L3→L4 跨度，其他案例仅作佐证。如果写到 §4 发现篇幅超过 §3 的两倍，就需要进一步压缩。

**自审计基础设施的涌现：**
- `evaluations.toml` 注册表——每个评估有结构化元数据
- `check-model-evaluations.sh` 在每次运行前审计注册表完整性
- Coverage Map 的规划规则 codified 了"L4 测试是功能交付的预期"

**读者在此获得的：** "Agent 不只是在运行测试——它在设计对抗性验证场景，映射覆盖缺口，维护审计基础设施。仓库的测试系统变成了一个自治的子系统。"

#### §4d. 为什么 Testing 是"自治实验室"的最佳证据

收束这个章节的论点：
- Constitution 的 Strange Loop 改变了系统对自己的理解
- Testing 的 Strange Loop 不仅改变了协议，还**改变了行为**——Agent 开始自发设计它之前无法想象的复杂测试
- 当一个系统的验证子系统开始自我设计、自我审计、自我演化，这就是"实验室"而不是"仓库"
- 从 `go test` 到 `logic-bomb` 只用了 43 天

### §5. Session/Closure 的故事（第三个 loop + 热力学视角）

**螺旋位置：** 第 5 圈——第三次确认模式 → 引入热力学视角。

这一章更简洁——读者已经两次看到 loop，不需要完整展开。重点是用第三个案例引出"为什么"。

**故事弧（快速）：**
- Agent 声称"完成"，但知识没有落地
- 下一个 Session 需要重新解释之前的讨论
- 意识到 Session 是 unbounded events queue
- 引入 Closure Protocol → 从 AGENTS.md 中分离成独立文档
- "Conversational completion is not closure."

**转向热力学视角：**

读者此时已经看到三个 Strange Loop 管理三种不同的东西：
- Constitution：系统身份
- Testing：验证标准
- Session/Closure：工作边界

**此时的问题是：为什么同一个模式在所有地方重复？**

答案是热力学的：
- 仓库自然趋向熵增（结构漂移、知识散落、状态重复）
- 每个 Strange Loop 都是一个局部的负熵机制
- 当 friction 出现时（熵增的信号），系统通过修复协议将熵压缩回可持续的水平
- 三个 loop 分别管理三种熵：身份熵、验证熵、边界熵

> "The repository naturally tends toward entropy—structural drift, scattered knowledge, duplicated state. You are the system's negentropy pump."
> "The goal is not minimum entropy, but *sustainable coherence*—enough structure to act reliably, enough flexibility to evolve."

**读者在此获得的：** "同一个模式之所以反复出现，是因为它们都在解决同一个根本问题：开放系统如何在时间中维持自己。"

### §6. 统一与分形

**螺旋位置：** 第 6 圈——所有概念回收，全景视角。

**分形呼应：同一个模式在不同尺度上重复**
- 每一次 Commit = 最小粒度的熵压缩（state transition）
- Closure Protocol = 单个 Session 的 Strange Loop + 熵管理
- Testing Protocol = 验证子系统的 Strange Loop + 熵管理
- Constitution = 整个仓库的 Strange Loop + 熵管理

**Quine 项目的自指性：**
- Quine 研究的是 Agent 作为 ephemeral process 的生存策略
- 这篇博客展示的是人类-Agent 协作中 Session 作为 ephemeral coupling surface 的生存策略
- Session 对于人类协作者 ≈ Context Window 对于 Agent Process
- 同一个问题，不同的尺度

**Quine 的本体论怪圈（简短提及，不展开）：**
- 项目取名 Quine——自复制程序，一个经典的自指性概念
- 项目的核心原则是自指性演化（Strange Loop as Article Zero）
- AGENTS.md 的迭代过程本身就是自指性演化的实例
- Quine 作为 AI Agent Runtime，研究的正是 Agent 如何在无状态中维持自身——而仓库的演化解决的是同一个问题
- 这是三层嵌套的 meta-strange-loop：名字自指 → 原则自指 → 演化过程自指
- **写作注意：** 点到为止，作为一个"会心一笑"的观察，不是本文论证重点。一两句话足够。读者应该感受到"连项目名字都是这个模式的一部分"的趣味，而不是被拉进另一篇文章。

**更深的统一——回扣标题：**
- 此时回收标题中的 "autopoietic"——读者已经看完三个 Strange Loop + 热力学解释，现在才有足够的经验基础来理解这个词
- Maturana & Varela 的 autopoiesis（自创生）：一个系统的组织方式使得它的运作过程不断再生产自身的组织方式
- 这正是我们在仓库中看到的：Constitution 的 Strange Loop 再生产 Constitution，Testing 的 Strange Loop 再生产 Testing Protocol，Closure 的 Strange Loop 再生产 Closure Protocol
- 物理学对应：dissipative structure（耗散结构）——远离平衡态的开放系统通过持续的能量耗散维持自身秩序
- **写作注意：** 这是"啊，原来标题说的是这个"的顿悟时刻。不需要长篇介绍 autopoiesis 理论，一两段话把仓库的行为映射到这个概念即可。读者到这里已经通过 43 天的 Git 历史"挣得"了这个理解。
