# Manuscript Plan: Successor Morphology Without Offspring Slots

## Argument Plan

1. Acknowledge that ALife already has rich morphology, morphospace,
   evo-devo, and evolutionary-robotics traditions.
2. Introduce the narrower Quine object: **successor morphology** as executable
   process organization after handoff.
3. Compare substrate-provided offspring slots with entity-constructed successor
   morphology.
4. Locate Quine as bounded trace-level autoconstructive successor formation.
5. Explain what Quine adds: process-native handoff, carrier topology burden,
   destructive `exec`, and delayed addressability.
6. Close with boundaries below metric-backed morphospace, open-ended evolution,
   and population selection.

morphology bridge. It should not try to beat classic ALife systems at their own
tasks. Its useful contribution is a role map: which reproduction semantics are
substrate-provided, which successor-forming work is performed by the entity,
and why process-native successor organization is a distinct ALife morphology
object.

## Substrate-Reproduction Argument

The manuscript should frame Quine as an unusually hard autoconstructive case
because POSIX supplies general execution physics rather than reproductive
semantics. The useful contrast is:

```text
classic digital-organism substrate:
  substrate allocates / places / scores offspring;
  entity fills or copies information within that reproduction grammar

Quine on POSIX:
  substrate supplies CPU, memory, files, processes, fds, syscalls, exec;
  entity must construct a successor body and preserve or rebuild the carrier
  through which future work will reach it
```

This yields four ALife-facing dimensions:

1. **Reproduction privilege removed:** no magic offspring API or slot.
2. **Carrier topology burden:** successor viability depends on reconstructed
   future-work channels, not only produced code.
3. **Morphological freedom:** POSIX admits heterogeneous successor bodies as
   long as they satisfy executable / interpreter conventions and carrier needs.
4. **Destructive replacement:** `exec` is a lifecycle bottleneck, not an
   additive spawn with the parent left intact.

Use this as theory/comparator material, not as an attack on Tierra, Avida, or
Pushpop. The point is to locate where each substrate places the reproduction
burden.

## Future Experiment / Analysis Design

This paper needs comparative analysis more than new Quine runs, but a few
experiments can strengthen the taxonomy.

| Design item | Question it answers | Expected manuscript role |
|-------------|---------------------|--------------------------|
| primary-source comparator table | Which systems are nearest and what do they actually claim? | core contribution |
| substrate-provided reproduction mini-model | What changes when an environment provides offspring slots versus Quine-style successor construction? | illustrative contrast |
| minimal control-compatible non-Quine successor | Is Quine's full runtime special, or is control-compatible organization enough? | Quine placement |
| variable successor morphology under fixed substrate | Can Quine produce multiple successor forms under systematically varied pressure while the substrate remains constant? | supports morphology claim |
| population-selection contrast | What would be required to move from trace-level viability to population-level autoconstructive evolution? | boundary / future work |

Design rule:

- do not claim Quine is mature autoconstructive evolution;
- use `bounded trace-level autoconstructive successor formation` until
  population, heredity, variation, and multi-generation selection are shown;
- keep novelty as taxonomy and process-native handoff, not open-endedness.
