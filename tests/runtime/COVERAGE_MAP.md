# Runtime Coverage Map

This document translates Quine's current runtime implementation into a coverage inventory.

It is intentionally broader than `./tests/runtime/run.sh`.
The point is not that every row needs `L5` today.
The point is that every meaningful runtime surface stays visible, so we can decide explicitly what gets `substrate`, `runtime`, `usage`, `discovery`, and `necessity` coverage.

Drift check: `./scripts/check-runtime-doc-sync.sh --strict tests/runtime/COVERAGE_MAP.md` for stale public-runtime phrasing and `./scripts/check-model-evaluations.sh --strict` for model-registry health, plus comparing `test_*` / `gate_*` functions in [`run.sh`](./run.sh) with the `L2` entries here.

## Layer Legend

| Layer | Meaning |
|------|---------|
| `L1` | `substrate` - deterministic Go tests |
| `L2` | `runtime` - live binary contract tests |
| `L3` | `usage` - model-layer mechanism-use checks |
| `L4` | `discovery` - unnamed mechanism discovery under affordance-visible pressure |
| `L5` | `necessity` - zero-hint pressure selection |

## Acceptance Status Language

Use the coverage rows as acceptance work items, not just as a feature list.

Interpret the "Main gap to close next" column with this status language:

- `runtime-only` - the claim currently stops below model-layer acceptance on purpose
- `usage-gap` - the runtime slice exists, but mechanism-use coverage is still missing or weak
- `discovery-gap` - the runtime slice and mechanism-use coverage exist, but clean unnamed discovery is still weak
- `necessity-gap` - the feature may be discoverable, but there is still no honest zero-hint pressure task
- `harness-gap` - the feature may exist, but current bridge, scorer, fixture, or preservation defects block trustworthy interpretation
- `closure-gap` - coverage exists, but the canonical claim, baseline, or failure interpretation is still too vague to call the feature solid

When updating a row, prefer naming the gap in one of these terms instead of
leaving "not done yet" implicit.

## Immediate Backlog

If the goal is to make runtime coverage feel materially less hollow, the next additions should be:

1. Port the env-boundary estate, which is the one row above whose live and
   model layers currently assert a mechanism that no longer exists: rewrite the
   five `run.sh` config blocks against the new boundary, port
   `staged-config-explicit-max-turns-reexec` (it is `acceptance="gate"`, so its
   port is sequencing-critical), then author the four remaining `L3` units and
   the three `L4` units. `shadowing-regression` is the one that matters and the
   one that cannot be auto-scored.
2. Add `L2` live contracts for `process-control/v1` or `world/v0` only after a
   specific runtime claim needs them; do not group those surfaces with
   `habitat/world/v0` or a maintenance-resident pilot as one spine.
3. Decide explicit claim boundaries for the newly surfaced env-controlled rows:
   shell execution envelope, response governance, context pressure,
   tape lineage, and provider shaping.
4. Add `L2` live contracts where the env control already changes runtime physics
   but only has `L1` proof today: especially timeout / truncation,
   exit-disable / impossibility posture, and lineage / retention propagation.
5. Redesign one `L4` family cleanly, most likely from `exec`, `switch-world`,
   `anchor-memory`, or `fork`, so we stop conflating explicit
   mechanism use with actual discovery.
6. Ship the first honest `L5` necessity task for a runtime primitive once
   zero-hint pressure can force the mechanism instead of narrating it.

## Planning Rule

When a new runtime feature lands:

1. add the feature here,
2. name the minimum required layer,
3. explain why higher layers are or are not needed,
4. name the current acceptance gap in concrete terms when the feature is not yet solid.

That keeps "what needs coverage?" from remaining tribal memory.
